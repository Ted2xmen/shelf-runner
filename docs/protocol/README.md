# shelf-runner protocol

shelf-runner talks to other apps through plain files and macOS distributed notifications. This
folder describes that contract. The current version is **1**; the full text is [v1.md](v1.md).

## What it is

The protocol is everything that crosses the runner's process boundary
([v1.md#1-scope](v1.md#1-scope)):

- **Markdown lines** in `AGENT-QUEUE.md` and `SCHEDULED.md`, each signed with HMAC-SHA256 over a
  canonical text.
- **A pairing code** (`SR1-...`) that carries the shared 32-byte key from the runner to the app that
  signs.
- **Distributed notifications**: the status broadcast, ping, signed commands and the log reply.
- **Files**: `heartbeat.json` (a status copy) and the `attach` `.command` scripts.

## Parties

| Party | Role |
|---|---|
| **Shelf** (closed source, Mac App Store) | the other end of the contract: appends signed queue lines, sends signed commands and pings, reads the status and log replies |
| **shelf-runner** (this repo) | reads the queue files, runs jobs in tmux, broadcasts status, verifies and executes commands |
| **[Runner Desk](https://github.com/Ted2xmen/runner-desk)** (open source) | read-only consumer: pings, reads the status, shows the runner's tmux windows through its own grouped sessions; sends no signed commands today |

A person can also play the producer role with the `shelf-runner line` CLI and any editor
(`Sources/shelf-runner/main.swift:136-151`).

## Version policy

- **Current version: 1**, `ProtocolV1.version` (`Sources/ShelfRunnerCore/Protocol.swift:6`).
- **The status and the log reply carry `v`**, both in `userInfo` and, for the status, inside the
  JSON (`Sources/ShelfRunnerCore/Bridge.swift:64`, `:114`, `Sources/ShelfRunnerCore/StatusV1.swift:5`).
- **Commands and pings carry no version** (`Sources/ShelfRunnerCore/Protocol.swift:85-87`). The
  canonical texts are tagged `q1` and `s1` (`Sources/ShelfRunnerCore/Protocol.swift:36`, `:42`) and
  the pairing code `SR1-` (`Sources/ShelfRunnerCore/Protocol.swift:136`); those tags are part of the
  signed or decoded data, not a negotiated version.
- **A consumer that sees an unknown `v`** should not guess: it should show "update shelf-runner" (or
  update itself) and stop reading the payload. This is consumer behavior, outside this repo.
- **Any change to a name, the canonical text, the signature scheme or the meaning of a field is a new
  version**: new fixtures under `fixtures/protocol/v<N>/`, a new `v<N>.md`, and a new `version`
  constant.
- **Adding an optional field within v1.** There is one precedent: `styles` was added to the log
  reply as an optional key that is left out when empty, and the old form without it still decodes
  (`Sources/ShelfRunnerCore/LogReply.swift:11-13`; both forms are fixtures, see
  `Tests/ShelfRunnerCoreTests/ProtocolFixtureTests.swift:425-431`).
  For the **status**, the code states no such rule: every key is always written, with explicit
  `null` for unknown values (`Sources/ShelfRunnerCore/StatusV1.swift:3`), and nothing in this repo
  says consumers ignore unknown keys. **Proposal:** a new status key may be added within v1 only if
  it is optional for consumers and all known consumers ignore unknown keys; removing a key or
  changing its type is always a new version.

## Fixtures

`fixtures/protocol/v1/` holds the machine-checked examples: test key, signed lines, commands,
status samples and log replies ([v1.md#15-fixtures](v1.md#15-fixtures)).

- They are generated by `Tests/ShelfRunnerCoreTests/ProtocolFixtureTests.swift`, the fixture
  `README.md` included (`Tests/ShelfRunnerCoreTests/ProtocolFixtureTests.swift:360-366`).
- `swift test` checks them byte for byte; `REGEN_PROTOCOL_FIXTURES=1 swift test --filter ProtocolFixture`
  rewrites them (`Tests/ShelfRunnerCoreTests/ProtocolFixtureTests.swift:6-8`, `:369-378`).
- Never edit them by hand. A change to the generated files is a protocol change: decide the version
  first (above).
- Consumers keep their own copies. There is no automated sync.
